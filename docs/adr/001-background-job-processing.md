# ADR-001: Фоновая обработка заданий

## Контекст и ограничения

Сервис принимает PDF-файл, создаёт задание (Job) и возвращает его идентификатор пользователю. Обработка выполняется асинхронно: OCR Tool извлекает текст, затем Statistics Tool подсчитывает количество слов и символов.

Обработка может занимать продолжительное время, а внешний OCR-сервис — отвечать с задержкой или не отвечать вовсе. Поэтому выполнение не должно зависеть от времени жизни HTTP-запроса.

Состояние Job должно сохраняться в базе данных. После перезапуска приложения система должна обработать задания, которые не успели завершиться.

В первой версии предполагается один экземпляр приложения. При этом необходимо ограничивать количество одновременно выполняемых заданий.

Жизненный цикл Job определён требованиями проекта:

- `created` — задание создано;
- `running` — задание обрабатывается;
- `done` — обработка успешно завершена;
- `failed` — обработка завершилась ошибкой.

Допустимые переходы: `created → running`, `running → done`, `running → failed`. Завершённые задания не возвращаются к выполнению.

## Решение

Для фоновой обработки используется `BackgroundService` из .NET. Он запускает Dispatcher, который получает задания из базы данных и выполняет этапы конвейера.

База данных является основным источником информации о состоянии и наличии заданий. Ожидающие задания не хранятся только в памяти приложения: после перезапуска задания в состоянии `created` остаются доступными для обработки.

Основные правила:

1. Dispatcher периодически проверяет наличие заданий в состоянии `created`.
2. Перед началом обработки Dispatcher атомарно переводит Job из `created` в `running`, чтобы одно задание не было одновременно захвачено несколькими исполнителями.
3. После успешного выполнения OCR Tool и Statistics Tool Dispatcher сохраняет результаты и переводит Job в `done`.
4. При критической ошибке Dispatcher сохраняет информацию об ошибке и переводит Job в `failed`.
5. Количество одновременно обрабатываемых заданий ограничивается настройкой приложения. Конкретное значение определяется после проверки производительности.

### Восстановление после перезапуска

В первой версии предполагается один экземпляр приложения. При запуске приложения задания, оставшиеся в состоянии `running`, переводятся в `failed` с кодом ошибки `processing_interrupted`.

Такое поведение сохраняет заданную модель переходов состояний и не допускает повторного запуска задания, которое могло частично выполнить обработку. Автоматическое продолжение такого задания в первой версии не предусматривается.

Повторный вызов OCR при тайм-ауте является отдельным механизмом: Dispatcher выполняет одну повторную попытку. Если обе попытки завершаются тайм-аутом, Job переводится в `failed`.

## Рассмотренные альтернативы

### 1. Выполнение обработки непосредственно в HTTP-запросе

В этом варианте сервер выполнял бы OCR и подсчёт статистики до отправки ответа пользователю.

Недостатки:
- Длительная обработка увеличивает время ожидания ответа.
- Соединение может быть прервано до завершения обработки.
- Выполнение зависит от времени жизни HTTP-запроса.

Вариант не выбран, поскольку обработка должна выполняться асинхронно и независимо от HTTP-запроса.

### 2. Fire-and-forget без сохранения очереди

В этом варианте приложение запускало бы фоновую задачу после получения запроса, не сохраняя надёжно информацию о необходимости её выполнения.

Недостатки:
- При перезапуске приложения незавершённые задания могут потеряться.
- Нельзя надёжно определить, какие задания ожидают выполнения.
- Сложнее контролировать состояние обработки.

Вариант не выбран, поскольку задания и их состояние должны сохраняться при перезапуске приложения.

### 3. Очередь только в оперативной памяти

В этом варианте задания помещались бы во внутреннюю очередь приложения, например `Channel<T>`.

Недостатки:
- Очередь теряется при перезапуске приложения.
- Для восстановления необходимо отдельно сохранять задания в БД.
- Возникает необходимость синхронизировать состояние очереди и состояние Job.

Вариант не выбран в качестве основного механизма хранения очереди. Очередь в памяти может использоваться позднее как дополнительный механизм оптимизации.

### 4. Отдельный Worker Service

В этом варианте HTTP API и фоновая обработка запускались бы как отдельные приложения.

Преимущества:
- Независимое масштабирование API и обработчиков.
- Возможность отдельно управлять ресурсами фоновой обработки.

Недостатки:
- Более сложные инфраструктура и развёртывание.
- Дополнительные вопросы взаимодействия компонентов.
- Для первой версии такое разделение не является необходимым.

Вариант не выбран для первой версии, но может быть рассмотрен при дальнейшем развитии проекта.

## Последствия решения

Положительные последствия:

- HTTP API не ожидает завершения длительной обработки.
- Состояния заданий и ожидающие задания сохраняются в БД.
- Количество одновременно выполняемых заданий можно ограничивать.
- Dispatcher централизованно управляет последовательностью выполнения Tools и обработкой ошибок.

Отрицательные последствия и ограничения:

- Dispatcher должен периодически обращаться к БД для поиска новых заданий.
- Необходимо атомарно захватывать задания, чтобы исключить их одновременный запуск.
- После перезапуска задания в состоянии `running` переводятся в `failed`, а не продолжают выполнение.
- Периодический поиск заданий создаёт дополнительную нагрузку на БД.
- В первой версии не предусматривается полноценная координация нескольких экземпляров приложения.

## Условия пересмотра решения

Решение следует пересмотреть, если:

- Появится необходимость запускать несколько экземпляров приложения.
- Объём заданий или время ожидания в очереди станут слишком большими для текущего механизма.
- Потребуется автоматически восстанавливать обработку после аварийного завершения.
- Возникнет необходимость независимо масштабировать API и фоновые обработчики.
- Нагрузка на БД из-за периодического поиска заданий станет существенной.

В этих случаях можно рассмотреть отдельный Worker Service, специализированную очередь сообщений или механизм аренды заданий (lease).
