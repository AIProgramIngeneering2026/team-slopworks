# ADR-003: Отмена Job не поддерживается

- **Дата:** 15.11.2026
- **Статус:** Accepted

## Контекст и ограничения

Клиент может передумать, пока Job выполняется. Жизненный цикл Job содержит состояния `created`, `running`, `done` и `failed`; переходы из конечных состояний запрещены.

Обработка одного Job состоит из вызова внешнего OCR и подсчёта статистики. Вызов, уже отправленный OCR-провайдеру, нельзя отозвать.

В первой версии нет аутентификации, поэтому сервис не может определить, кто вправе отменить задание.

## Решение

Операция отмены не предоставляется. Принятый Job выполняется до `done` или `failed`. Клиент, которому результат больше не нужен, не запрашивает его. Состояние `cancelled` не вводится.

## Рассмотренные альтернативы

### 1. `DELETE /jobs/{id}` с состоянием `cancelled`

Отмена в `created` и в `running` через `CancellationToken`, который уже передаётся в `ITool.ExecuteAsync`.

Недостатки:

- Новое конечное состояние и переходы `created → cancelled`, `running → cancelled`.
- Гонка отмены с завершением: нужно атомарно определять, какое изменение применяется.
- Работа OCR-провайдера по уже отправленному вызову выполняется и оплачивается.
- Без аутентификации отменить задание может любой, кто знает его `id`.

Вариант не выбран: для первой версии стоимость реализации выше пользы.

### 2. Отмена только в `created`

Проще первого варианта: Job ещё не захвачен Dispatcher, инструменты не вызывались.

Недостатки:

- Задание находится в `created` недолго, запрос отмены почти всегда опоздает.
- Всё равно нужны новое состояние, операция API и решение о правах доступа.

Вариант не выбран по тем же причинам.

## Цена решения

- Ресурсы OCR тратятся на задания, результат которых клиенту не нужен.
- Клиент не может освободить слот обработки, занятый ошибочно отправленным документом.

## Условия пересмотра решения

- Появится аутентификация и понятие владельца задания.
- Обработка одного Job станет заметно дольше тайм-аута OCR, например при постраничной обработке.
- Стоимость вызовов OCR станет существенной.
