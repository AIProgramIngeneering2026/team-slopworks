# ADR-002: Хранение файлов и данных

- **Дата:** 2026-11-15
- **Статус:** Proposed
  
## Контекст и ограничения

Сервис принимает PDF-файлы и сохраняет результаты их обработки. Необходимо хранить:

- исходные PDF-документы;
- информацию о заданиях и их состояниях;
- ссылки на сохранённые файлы;
- результаты OCR и статистику;
- информацию об ошибках обработки.

В первой версии проекта используется SQLite. Взаимодействие с базой данных выполняется через Entity Framework Core. В дальнейшем предусмотрена возможность перехода на PostgreSQL.

Исходные PDF планируется хранить отдельно от основной базы данных — в локальной файловой системе.

Файловая система и БД не поддерживают общую транзакцию. Поэтому необходимо учитывать частичные сбои, например ситуацию, когда файл уже сохранён, а запись Job ещё не создана.

## Решение

### 1. Хранение данных в базе данных

Для хранения заданий и результатов используется реляционная база данных SQLite. Взаимодействие с ней выполняется через Entity Framework Core, схема управляется с помощью миграций.

В БД хранятся:

- идентификатор и состояние Job;
- параметры обработки;
- ссылка на исходный PDF-файл;
- распознанный текст;
- результаты подсчёта статистики;
- информация об ошибке, если обработка завершилась неуспешно.

При проектировании модели данных следует по возможности избегать зависимости бизнес-логики от особенностей конкретного провайдера БД.

Переход с SQLite на PostgreSQL потребует проверки совместимости схемы, запросов и миграций. Он не рассматривается как гарантированная замена одной настройки конфигурации.

### 2. Хранение PDF-файлов

Исходные PDF хранятся в локальной файловой системе.

Для работы с файлами вводится абстракция `IFileStorage`. Её реализация `LocalFileStorage` отвечает за сохранение, чтение и удаление файлов. Другие компоненты приложения используют интерфейс хранилища, а не обращаются к файловой системе напрямую.

Интерфейс предоставляет операции сохранения файла, открытия его для чтения и удаления.

В БД хранится ключ файла в хранилище, а не абсолютный путь. Это позволяет не связывать остальные компоненты с конкретной директорией и реализацией файлового хранилища.

OCR Tool получает поток (`Stream`) для чтения PDF и не знает, где физически находится файл.

### 3. Согласованность файловой системы и БД

Поскольку файловая система и БД не участвуют в одной общей транзакции, сохранение PDF и создание Job выполняются в следующем порядке:

1. Принятый PDF сохраняется в файловом хранилище.
2. После успешного сохранения создаётся запись Job в БД со ссылкой на файл.
3. Если создание записи Job завершается ошибкой, сохранённый файл удаляется в рамках компенсирующего действия.
4. Если удалить файл не удалось, он считается потенциально неиспользуемым и должен быть обнаружен механизмом очистки.

Для временных файлов может использоваться промежуточное сохранение с последующим переносом в основное расположение.

Механизм очистки должен находить файлы, на которые не ссылаются существующие задания. Периодичность очистки и условия, при которых файл можно считать неиспользуемым, определяются при реализации. В частности, необходимо исключить удаление файла, который уже сохранён, но для которого запись Job ещё создаётся.

## Рассмотренные альтернативы

### 1. Хранение PDF непосредственно в БД

В этом варианте содержимое PDF сохранялось бы в таблице базы данных в виде бинарных данных.

Недостатки:
- Увеличение размера базы данных.
- Дополнительная нагрузка на БД при чтении и записи больших файлов.
- Смешивание хранения файлов и структурированных данных.
- Более сложное резервное копирование и обслуживание БД при большом объёме файлов.

Вариант не выбран, поскольку исходные PDF удобнее хранить отдельно от данных о заданиях.

### 2. Прямая работа компонентов с файловой системой

В этом варианте компоненты приложения самостоятельно работали бы с путями и файловыми операциями.

Недостатки:
- Компоненты зависели бы от конкретного способа хранения файлов.
- Изменение файлового хранилища потребовало бы изменений в нескольких местах приложения.
- Логика работы с файлами могла бы дублироваться.

Вариант не выбран. Вместо него используется абстракция `IFileStorage`.

### 3. Облачное или объектное хранилище

В этом варианте PDF сохранялись бы во внешнем объектном хранилище.

Преимущества:
- Возможность хранить большие объёмы файлов.
- Независимость от локального диска приложения.
- Возможность масштабировать хранение отдельно от приложения.

Недостатки:
- Дополнительная инфраструктура и конфигурация.
- Зависимость от внешнего сервиса.
- Необходимость учитывать сетевые ошибки и особенности доступа к объектам.

Вариант не выбран для первой версии, поскольку локальной файловой системы достаточно для текущего объёма проекта.

## Последствия решения

Положительные последствия:

- Файлы хранятся отдельно от структурированных данных и результатов обработки.
- Компоненты приложения не зависят от конкретной реализации файлового хранилища.
- OCR Tool получает поток данных, а не путь к файлу.
- EF Core позволяет управлять схемой БД с помощью миграций.
- В дальнейшем можно реализовать другую версию `IFileStorage`, например для объектного хранилища.

Отрицательные последствия и ограничения:

- Согласованность файловой системы и БД необходимо обеспечивать на уровне приложения.
- При сбоях могут появляться файлы, не связанные с существующими заданиями.
- Необходим механизм безопасного обнаружения и очистки неиспользуемых файлов.
- Переход с SQLite на PostgreSQL потребует проверки совместимости и тестирования.
- Локальное файловое хранилище ограничивает масштабирование нескольких экземпляров приложения без дополнительной настройки общего доступа к файлам.

## Условия пересмотра решения

Решение следует пересмотреть, если:

- Объём PDF-файлов станет слишком большим для локального хранилища.
- Появится необходимость запускать несколько экземпляров приложения на разных серверах.
- Возникнет потребность в облачном или объектном хранении файлов.
- Появятся требования к более сложному резервному копированию и восстановлению файлов.
- SQLite перестанет удовлетворять требованиям по нагрузке или конкурентному доступу к данным.

В этих случаях можно рассмотреть объектное хранилище, например S3-совместимое, и переход на PostgreSQL.
