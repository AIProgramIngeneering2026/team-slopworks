## Правила работы с MR

### Сдача на ревью

При сдаче ветки на ревью перед сливанием в основную ветку выполняем чек-лист:

1. Ветка актуальна относительно таргет-ветки, не имеет конфликтов (кроме исключений по договоренности). При актуализации свой ветки, удостоверится что локальная версия таргет ветки актуальна.
2. Полностью просмотрен diff на наличие ошибок, недоработок. Автор кода уверен (кроме исключений по договоренности) , что:
   1. Код чист, не повторяет существующую функциональность, декомпозирован и расширяем
   2. MR не приносит за собой изменения вне скопа задачи, где это возможно
3. Проведен самостоятельный код-ревью вместе с агентом (`/review`, `/code-review`) если есть такая возможность
4. Название MR и ветки соответствует правилам
5. В описании MR кратко расписаны основные изменения. Если изменена, убрана или внедрена работа с данными, в описании приложена [DFD-диаграмма](https://ru.wikipedia.org/wiki/DFD) на [mermaid](https://en.wikipedia.org/wiki/Mermaid_(software))

### Работа с комментариями

После получения фидбека на ревью:

1. Прочитать комментарий и изучить суть проблемы. Ревьюверы тоже ошибаются, на ошибки нужно указывать. Нельзя действовать без понимания проблемы. Если нет понимания проблемы или как её исправить, выносить на обсуждения с ревьювером или командой.
2. Если в комментарии указан вопрос, то ответить на него. Комментарий - не всегда призыв к действию. 
3. После исправления проблемы поставить реакцию на комментарий ревьювера, не закрывать тред. Если действий не предпринято, или исполнитель не согласен с комментарием ревьювера - ответить на комментарий и не ставить реакцию
4. После того, как все проблемы разрешены и изменения отпушены, повторно прочитать diff и убедится что проблем не осталось
5. Запросить повторный ревью

### Назначение ревьюверов

Ревью проводится по кругу. Каждый PR назначается на закреплённого ревьювера:

| Автор PR | Ревьювер |
| --- | --- |
| @txssu | @Kexogg |
| @Kexogg | @var1etas |
| @var1etas | @VladaAlmazova |
| @VladaAlmazova | @txssu |

Правила:

1. PR сливается только после approve закреплённого ревьювера, кроме случая из пункта 3. Автор не может одобрить свой PR.
2. Если закреплённый ревьювер не ответил в течение 48 часов, автор назначает любого другого участника и сообщает об этом в чате команды. Если до срока сдачи осталось меньше 48 часов, ревьювера можно заменить раньше.
3. Если провести ревью до срока сдачи некому, автор может влить PR самостоятельно. Причину автор описывает в разделе «Препятствия» отчёта по практике.
4. Ревью должно содержать вопросы или замечания по сути.
5. Ревьювер проверяет соответствие PR задаче и критериям приёмки, корректность и читаемость кода, наличие тестов, выполнение Definition of Done.
6. PR сливает автор после approve и разрешения всех тредов.

## Definition of Done

Задача считается выполненной, когда выполнены все применимые пункты:

1. Реализованы все критерии приёмки из issue и связанного сценария в `docs/requirements.md`.
2. Код проходит сборку без ошибок и новых предупреждений.
3. Добавлены автотесты: позитивные и негативные случаи для новой логики. Все тесты проходят.
4. При изменении API обновлён контракт OpenAPI, ошибки возвращаются в едином формате.
5. При изменении схемы данных добавлена миграция, она применяется на чистой базе.
6. При изменении архитектуры или ключевом техническом решении обновлены диаграммы или добавлен ADR.
7. При изменении работы с данными в описание PR приложена DFD-диаграмма.
8. В репозитории нет секретов, новая конфигурация читается из окружения и описана в README.
9. Выполнен чек-лист сдачи на ревью, PR одобрен по правилам ревью, все треды разрешены.
10. PR влит в `main`, связанный issue закрыт.

## Конвенции названий

### Merge request

`<category>: <short-description>`
Пример: `feat: add opentelemetry`

Называть MR нужно на английском языке в imperative/base present simple. Обязательно должен быть глагол. Название должно фокусироваться на том, что MR делает
Как можно:
`feat: add opentelemetry`
Как нельзя:
`crashes` - нет глагола, нет информации о том, какие изменения вносит MR, нет категории
`telemetry does not work` - констатация факта вместо информации об изменении, нет категории

### Ветки

`<category>/<short-description>`
Пример: `feat/openeteletry`

### Коммиты

`<type>: <short-description>`
Пример: `feature: add opentelemetry instumentation`
